선택 순서를 한 곳에

같은 버튼이 상황 스킬, 연계의 다음 동작, 단발 스킬 중 무엇이 될지를 한 함수에서 정해진 순서로 결정합니다. 입력이 어떤 스킬이 되는지 추적할 곳이 하나뿐입니다.

검증과 발동 직전 보정의 분리

전투 상태 전환, 대시 공격 교정, 회피 방향 설정을 검증 앞에서 하면 검증에 떨어진 스킬도 캐릭터 상태를 바꿉니다. 이 처리를 검증 뒤로 옮겨 통과한 스킬만 상태를 바꾸게 했습니다.

예약 경로 하나로

스킬 예약이 두 갈래로 나뉘어 있던 것을 행동 기록(ActionHistory) 하나로 합치고, 스킬 정지 흐름과 연계 종료 시점을 함께 정리했습니다. 지금 연계 스킬의 "정지 → 예약 또는 발동" 구조가 이때 만든 것입니다.

입력 정보를 끝까지 전달

어떤 버튼을 어떻게 눌렀는지를 스킬 옵션에 실어, 발동 단계와 다른 파티원 화면의 재생이 같은 입력 정보로 상태를 판단하게 했습니다.

핵심 구현 로직

검사와 소모의 분리

차단 조건을 순서대로 검사하는 단계, 실제 발동, 자원 차감·쿨타임 등록·서버 요청 단계를 나눴습니다. 검증에서 떨어진 스킬이 자원을 깎는 일이 구조적으로 생기지 않습니다.

클라이언트 선검증

서버 응답을 기다리기 전에 클라이언트가 자원을 먼저 확인해, 자원이 모자란 상태의 불필요한 왕복과 입력이 씹히는 느낌을 없앴습니다. 이후 구조가 바뀌어 지금은 이 클라이언트 검증이 발동 판정 자체이고, 스킬 패킷은 멀티플레이에서 다른 파티원에게 알리는 용도로만 나갑니다.

쿨타임 세 겹

파티 전체가 함께 쓰는 쿨타임, 게이지형 쿨타임, 스킬별 쿨타임을 한 판정 함수에서 순서대로 봅니다. 전투 상태가 전환되면 스킬 집합과 쿨타임 데이터를 새로운 상태에 맞게 재초기화합니다.

기술적 문제 해결

락온 대상이 죽어도 풀리지 않음

재탐색 분기가 이전 대상을 기준으로 다시 고른 뒤 항상 반환해, 죽은 대상을 계속 골랐습니다. 분기를 “이전 대상이 타겟 가능하고 조건에 맞을 때만 반환”으로 바꿔, 나머지는 일반 검색으로 흘러 다른 적으로 넘어가거나 해제되게 했습니다. 같은 작업에서 점수제 검색 태스크를 지우고 설정값 이름을 정리했습니다.

시전 중에 스킬 대상과 락온 대상이 갈라짐

매 틱 재탐색이 스킬 시전 중에도 돌아, 시전 중인 스킬의 대상과 락온 마커 · 카메라의 대상이 달라졌습니다. 재탐색 전에 행동 가능 여부를 보고, 막혀 있으면 그 틱은 유지만 하게 했습니다.

실패한 자리는 건너뛰고 경고만 남김

위치를 만드는 일은 판정(ExecCollision)이 맡고, 소환 프로퍼티는 목록을 받아 소비만 합니다. 기존 방식은 Exec 행을 여러 개 두면 고르게 퍼뜨리기 어렵고, 판정을 여러 번 하면 시간차가 생겼습니다. “판정 1회 + 위치 목록 일괄 소비”로 균등 배치와 동시 생성을 함께 얻었습니다. 기획 입력은 개수와 면적 비율 두 칸이고, 중심은 기존 기준 축과 위치 칸을 그대로 씁니다.

시전 위치 (중심에서 거리)

파란 원은 레벨 컬리전, 점선은 소환물 반지름만큼 안쪽 경계, 연한 파란 원이 최종 범위입니다. 보라 원은 장애물 유닛, 노란 점이 소환 위치입니다. 같은 시드면 어느 클라이언트에서도 같은 배치가 나옵니다.

핵심 구현 로직

  • 범위 원반지름은 레벨 컬리전 반지름 × √(p/100)으로 잡아 면적이 정확히 p%가 되게 합니다. 원이 컬리전 밖으로 넘치면 넘친 만큼만 중심을 안쪽으로 밀어, 모든 점이 컬리전 안에 있고 벽에서 소환물 반지름 이상 떨어지도록 했습니다.
  • 고른 배치원을 같은 면적의 슬롯 n개로 나누고 슬롯마다 황금각만큼 돌려 배치한 뒤(해바라기 배치), 슬롯 주변에서 조금씩 흔들어 뽑습니다. 최소 간격은 평균 간격에서 정해 서로 붙지 않게 했습니다.
  • 장애물 회피생성 순간 컬리전 안에 있는 몬스터 · 보스 · 프롭 등 살아 있는 유닛의 캡슐과 겹치지 않게 하고, 내비게이션 바닥 위인지, 영웅이 지나갈 수 없는 콜리전과 겹치지 않는지 검사합니다.
  • 항상 끝나는 폴백슬롯에서 정해진 횟수 안에 못 뽑으면 범위 전체 후보 중 가장 먼 점, 그다음 간격 조건을 뺀 가장 먼 점 순으로 물러납니다. 그래도 없으면 그 개체만 건너뜁니다. 범위 · 장애물 · 바닥 조건은 어느 단계에서도 완화하지 않습니다.
  • 시드 공유 난수Exec의 굴림 키로 시드를 만든 난수를 써서, 위치를 주고받는 패킷 없이도 클라이언트마다 같은 배치 모양이 나오게 했습니다.

기술적 문제 해결

판정이 n번 돌면 n × n개 소환

기존 반복 판정 구조에 새 방식을 그대로 얹으면 판정 회차마다 n개가 생깁니다. 위치 목록은 첫 요청에서 한 번만 만들고, 소환 프로퍼티에 Exec당 1회 가드를 두었습니다.

기존 랜덤 위치의 중심 쏠림 · 클라이언트 간 불일치

기존 랜덤 위치는 거리를 0~R에서 그대로 뽑아 중심에 몰리고, 클라이언트마다 다른 난수를 썼습니다. 새 방식은 면적 기준으로 거리를 뽑고 시드를 공유합니다. 기존 Random 계열 코드는 바꾸지 않았습니다.

소환 1개 생성 코드 중복

소환 하나를 만드는 처리를 함수로 분리해 기존 단일 소환과 새 일괄 소환이 같이 쓰게 했습니다. 기존 단일 소환의 동작은 그대로입니다.

데이터 없이 시험

기획 데이터가 들어오기 전에 콘솔 변수로 지정한 Exec의 판정 행을 시험용 값으로 덮어써, 실제 보스 패턴에서 배치를 미리 확인했습니다.

대상의 좌우 점이 동시에 박스 밖이면 한 번의 회전으로 둘 다 넣을 수 없는데, 마지막에 벗어난 쪽만 기억해 매 프레임 방향이 뒤집혔습니다. 느린 보정은 한쪽만 벗어났을 때로 제한하고 양쪽은 빠른 보정에 맡겼습니다.

기술적 문제 해결

풀에 반납된 홀더가 스택에 남음

홀더는 해제되지 않고 재사용되는 풀 객체라, 정지 순서가 어긋나면 반납된 뒤에도 포인터가 스택에 남았습니다. null 검사로는 잡히지 않아 풀 관리자에게 반납 상태를 묻고, 반납된 홀더는 콜백 없이 버리게 했습니다. 맵 전환 때는 매니저를 반납하지 않고 초기화해 재사용하고, 모든 연출을 멈춘 뒤에만 정리하도록 순서를 고정했습니다.

카메라 설정 키가 두 번 정지

스택에서 밀려날 때 매니저가 한 번, 연출이 끝날 때 홀더가 한 번 멈췄습니다. 키 상태를 없음 · 재생 · 정지 열거형으로 바꾸고, 재생 중이 아니면 정지를 무시해 멱등하게 만들었습니다.

구현 성과

중첩 카메라 복구 이슈를 구조로 닫았고, 카메라 설정 키와 카메라 이동 키가 같은 우선순위 규칙을 따릅니다. 스킬 · 효과 · 버프 연출을 그룹 ID로 간접 참조하게 바꿔, 외형별 선택 연출은 테이블 행을 더하는 것으로 붙습니다. 코스튬이 없거나 별도 설정이 없으면 기본 행으로 떨어지고, 소환수는 소환주의 코스튬을 따릅니다. 최근에는 연출 중 시점 입력을 막을 때 모바일 터치 회전도 함께 막고, 해제 직후 카메라가 튀지 않게 했습니다.

EzerKit 카메라 시뮬레이터

에디터를 켜고 스킬을 직접 써 봐야만 볼 수 있던 연출 카메라를, 프레임 단위로 재현해 브라우저에서 확인하게 만든 도구. 재현하는 과정에서 게임 코드의 버그를 찾아 고쳤습니다

해결한 문제

스킬 연출에 들어가는 카메라 키가 카메라를 실제로 어떻게 움직이는지 보려면 에디터에서 스킬을 직접 써 봐야 했습니다. 카메라는 레이어 스택, 대기 중인 키, 보간 중간값, 입력 차단, 플레이어 입력과 흔들림의 합으로 움직이는데 이 가운데 화면에 보이는 것은 결과뿐입니다. “왜 이 연출에서만 카메라가 튀는가”의 답은 코드를 읽는 사람 머릿속에만 있었고, 넣어도 효과가 없거나 이름과 다르게 동작하는 설정 칸도 문서 없이 섞여 있었습니다.

보간 방식

이전 방식은 프레임마다 “남은 거리 × 속도 × 프레임 시간”만큼 이동합니다. 바꾼 방식은 이동 비율을 1 − e−λ·시간으로 계산하고, λ는 60fps에서 이전과 같은 결과가 나오도록 환산합니다.

이 차이를 실제 연출에서 재려고 시뮬레이터에 이전 방식과 바꾼 방식을 모두 넣었습니다. 전체 연출을 60fps로 돌린 결과는 이전 코드와 위치 차이가 0이었고, 같은 시각의 카메라 위치 편차는 20fps에서 최대 120cm → 77cm, 30fps에서 60cm → 44cm로 줄었습니다. 이 확인을 거친 뒤 게임 코드의 카메라 보간을 바꿨습니다.

발견 및 개선

C++를 같은 순서로 옮기면 “코드가 실제로 하는 일”이 그대로 드러납니다. 후보마다 실데이터에서 해당 조건을 세어 영향 범위를 확인한 뒤, 영향이 분명한 것은 고치고 의도 확인이 필요한 것은 근거와 함께 남겼습니다.

발견실데이터 영향조치
프레이밍 카메라가 직전 프레임의 최종 출력 회전을 다음 목표의 출발점으로 되먹임해, 입력·흔들림·각도 오프셋이 매 프레임 누적락온 프레이밍 카메라 연출 결과가 최대 60°까지 어긋남출발점을 합산 전 값으로 변경 (한 줄)
유닛이 죽어도 다른 카메라 레이어에 저장된 대상이 남아, 레이어가 복원되면 죽은 유닛이 다시 잡힘레이어 대상을 쓰는 전투 카메라 전반사망 처리에서 레이어 대상까지 정리
레이어만 지정하고 설정을 비운 카메라 키가 기존 카메라 설정을 지움켜진 키 18개설정이 유효하지 않으면 아무것도 하지 않음
대상을 함께 잡는 카메라가 대상이 없을 때 월드 원점을 바라봄대상이 해제되는 순간대상이 없으면 따라가는 유닛의 등 뒤에서 같은 방향을 봄

터치 차단은 전역 입력 차단에 연동하면 한 줄로 끝나지만, 그렇게 하면 터치만 열어 두는 다른 화면의 의도가 깨집니다. 네 가지 방식을 비교해 영향이 연출 차단 키에 한정되는 방식을 골랐습니다.

해결한 문제

게임 데이터는 수많은 엑셀 파일과 시트에 나뉘어 있었습니다. 같은 파일을 여러 사람이 동시에 고치면 한쪽 작업이 덮어써졌고, 칸의 타입이나 다른 테이블 참조가 틀려도 엑셀에서는 알 수 없어 익스포트나 인게임에서야 문제가 드러났습니다. 데이터 하나가 어디에 연결되는지는 ID를 손으로 따라가야 했고, 값의 의미를 설명하는 문서는 실제 코드와 따로 놀았습니다.

주요 기능

  • 초안 → 테스트 → 반영여러 사람이 같은 시트를 동시에 각자의 초안으로 고칩니다. 내 초안을 반영한 JSON · CSV를 내 PC로 받아 인게임에서 먼저 확인하고, 반영할 때는 행 · 칸 단위로 자동 병합해 같은 칸을 서로 다르게 고친 경우만 고르게 했습니다.
  • 입력 단계 검사스키마의 타입, enum, 다른 테이블 참조, 조건식으로 칸마다 바로 검사합니다. 새로 고친 칸의 오류는 저장할 수 없고, 원래 있던 오류는 따로 표시해 작업을 막지 않습니다.
  • 연결 데이터 탐색키워드로 모든 테이블을 찾고, 고른 데이터의 구성과 쓰는 곳을 계층 · 노드 그래프로 펼칩니다. 스킬은 판정이 언제 어디서 켜지는지 재생하고, 던전은 배치를 위에서 내려다본 그림으로 봅니다.
  • 같은 결과로 내보내기기존 엑셀 익스포터가 만들던 클라이언트 JSON과 서버 CSV를 같은 형식으로 재현해, 게임 코드와 빌드 파이프라인을 바꾸지 않고 원본만 웹으로 옮길 수 있게 했습니다.
  • 코드 기준 가이드enum, 치트, 판정 범위, 스탯 설명을 C++ 코드에서 읽어 사전으로 만듭니다. 코드가 바뀌면 변경을 감지해 AI가 설명 초안을 쓰고, 사람이 승인한 것만 반영합니다.
